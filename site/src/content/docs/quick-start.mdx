## Install

Install the command-line tool with Cargo:

```sh
cargo install sprawl-guard
```

Or add it to a Node.js project (Node.js 22 or newer):

```sh
npm install --save-dev @kpozin/sprawl-guard
```

The examples on this site run `sprawl-guard` directly. In a Node.js project, run it as
`npm exec -- sprawl-guard` or `pnpm exec sprawl-guard` instead.

To confirm that what you installed was built by the Sprawl Guard release workflow, follow
[Verify a release](https://github.com/kpozin/sprawl-guard/blob/main/SECURITY.md#verify-a-release).

## Check a repository

Run these commands from the repository root.

<Steps>

1. Create the configuration file, `sprawl-guard.toml`.

   ```sh title="Initialize a repository"
   sprawl-guard init
   sprawl-guard init --write
   ```

   The first command shows the file, and the second writes it. Until you add settings to it,
   Sprawl Guard uses its built-in limits: 400 lines per file (800 for test files) and 10 source
   files directly inside each directory. To change them, see
   [Configure checks](/sprawl-guard/configure-checks/). If the project already uses an ESLint or
   Oxlint `max-lines` rule, you can
   [start from that rule](#start-from-a-max-lines-rule) instead.

2. Run the check.

   ```sh title="Run the first check"
   sprawl-guard check
   ```

   A passing check prints:

   ```text
   Configuration: sprawl-guard.toml

   No sprawl-guard violations found.
   Checked 2 source files in 2 directories across 2 languages.
   ```

   A failing check names each file or directory over its limit:

   ```text
   Configuration: sprawl-guard.toml

   Files over the line limit:

     src/large.py: 430 lines (limit 400)
       language: Python, counting code
   ```

</Steps>

If the check passes, commit `sprawl-guard.toml` and [add the check to CI](/sprawl-guard/run-in-ci/).

## Record existing violations

An existing repository usually has files and directories over the limits. Instead of fixing them
all before you can start, record them in a ratchet file, `sprawl-guard.ratchet.toml`. The check
then allows each recorded violation at its current size. It fails if a recorded violation grows,
and also if it shrinks, until you record the smaller size.

<Steps>

1. Preview the violations to record.

   ```sh
   sprawl-guard update
   ```

   ```text
   Ratchet changes:
   + add src/large.py (production lines): none -> 430
   + add src/flat (production direct files, group: source): none -> 12

   Preview only; use --write to apply.
   ```

   A directory entry also names the language group whose files it counts, as
   [How checks work](/sprawl-guard/reference/how-checks-work/) explains.

   If the list includes generated or third-party code, exclude those paths in
   [the configuration](/sprawl-guard/configure-checks/#choose-which-files-to-check) and preview
   again.

2. Write the ratchet file and run the check.

   ```sh
   sprawl-guard update --write
   sprawl-guard check
   ```

   ```text
   Configuration: sprawl-guard.toml

   No sprawl-guard violations found.
   Checked 14 source files in 2 directories across 1 language.
   Passed with 2 ratchet entries remaining.
   ```

3. Commit `sprawl-guard.toml` and `sprawl-guard.ratchet.toml` together.

</Steps>

Next, [add the check to CI](/sprawl-guard/run-in-ci/), then read
[Work with the ratchet](/sprawl-guard/ratchet/) to see how to record improvements.

## Start from a `max-lines` rule

If the project already limits file length with the ESLint or Oxlint `max-lines` rule, you can import
the rule's limit and the files it exempts. Sprawl Guard runs the project's own linter with Node.js,
so install the linter in `node_modules` first. Sprawl Guard is tested with ESLint 8.57 and 10, and
with Oxlint 1.93.

<Steps>

1. Preview a configuration based on the rule, then save it. ESLint can configure each file
   differently, so name a source file whose limit you want:

   ```sh
   sprawl-guard config import eslint src/index.js
   sprawl-guard config import --write eslint src/index.js
   ```

   For Oxlint, run `sprawl-guard config import oxlint`, then
   `sprawl-guard config import --write oxlint`.

   If `sprawl-guard.toml` already exists, `--write` fails. Copy the printed `[languages]` tables
   into the file instead.

2. Preview [ratchet entries](#record-existing-violations) for the oversized files that the linter
   exempts, then save them:

   ```sh
   sprawl-guard update --import eslint
   sprawl-guard update --import eslint --write
   ```

   For Oxlint, pass `--import oxlint`.

3. Run `sprawl-guard check`, and compare its results with the linter's. The two tools count lines
   slightly differently. The check also applies limits that the linter doesn't: the number of files
   directly inside each directory, and the length of files in other languages.

4. Preview the remaining violations with `sprawl-guard update`, and fix any that you don't want to
   accept. Then [record the rest](#record-existing-violations) with `sprawl-guard update --write`.

5. Remove the `max-lines` rule from the linter's configuration, then commit that change together
   with `sprawl-guard.toml` and `sprawl-guard.ratchet.toml`.

</Steps>

The CLI reference explains how Sprawl Guard
[reads the rule](/sprawl-guard/reference/cli-and-output/#config-import-eslintoxlint) and
[which exemptions it imports](/sprawl-guard/reference/cli-and-output/#update-paths).
