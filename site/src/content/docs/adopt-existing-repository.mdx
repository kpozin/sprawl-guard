---
title: Adopt Sprawl Guard in an existing repository
description: Record existing violations without allowing them to grow.
---

import { Steps } from "@astrojs/starlight/components";

You can adopt Sprawl Guard without first fixing every file or directory that exceeds the desired
limits.

Adoption uses two files with different jobs. `sprawl-guard.toml` defines the policy. A second file
records current measurements that exceed that policy so they may remain temporarily but cannot
grow. Sprawl Guard calls this second file the ratchet.

The commands below use `sprawl-guard` directly. For a project-local Node dependency, run them
through `npm exec -- sprawl-guard` or `pnpm exec sprawl-guard` instead.

<Steps>

1. Create the policy configuration.

   Preview the generated configuration, then create `sprawl-guard.toml`:

   ```sh
   sprawl-guard init --dry-run
   sprawl-guard init
   ```

   Edit the generated file to [set the desired limits](/sprawl-guard/configure-checks/), not the repository's current maxima. Use `sprawl-guard config resolved` to review the complete policy.

2. Record existing violations.

   After setting the policy, preview the proposed ratchet before writing it:

   ```sh
   sprawl-guard update
   sprawl-guard update --write
   sprawl-guard check
   ```

   A preview lists only the proposed changes:

   ```text
   Ratchet changes:
   + add file src/large.py [production] max_loc: none -> 430
   + add directory src/flat [production, source] leaf_files: none -> 12

   Preview only; use --write to apply.
   ```

   To inspect the complete TOML before writing, run `sprawl-guard update --format toml`. The resulting file looks like:

   ```toml title="sprawl-guard.ratchet.toml"
   #:schema https://kpozin.github.io/sprawl-guard/schemas/v1/sprawl-guard.ratchet.schema.json
   schema_version = 1

   [[files]]
   path = "src/large.py"
   role = "production"
   max_loc = 430

   [[directories]]
   path = "src/flat"
   role = "production"
   group = "source"
   leaf_files = 12
   ```

   File entries are identified by path and role. Directory entries are identified by path, role, and language group. The ratchet stores measured ceilings, not configuration limits or justifications.

3. Review and commit both files.

   The write creates the ratchet file selected by `[ratchet].file` in `sprawl-guard.toml` and adds its editor schema directive. Its default path is `sprawl-guard.ratchet.toml`. Review every entry. Keep entries only for maintained code that is expected to improve. Exclude generated or third-party code, and use a documented override for a deliberate long-term exception.

   If a ratchet file already exists, `update` adds newly discovered entries and preserves existing ceilings. Pass paths to limit discovery to selected files or directories. Raising an existing ceiling requires `--allow-increases`; review any increase carefully.

   Commit `sprawl-guard.toml` and `sprawl-guard.ratchet.toml` together. Confirm that the unchanged tree passes. Then temporarily increase one ratcheted measurement to verify that the ratchet rejects growth.

</Steps>

## Approve Later Exceptions

After adoption, scope deliberate approvals to the affected file or directory. For new temporary
debt, preview `sprawl-guard update PATH`, review the added ceilings, then repeat with `--write`. To
permit an existing violation to grow, use `sprawl-guard update PATH --allow-increases` for both
preview and write; raised ceilings are marked `! raise`.

For a permanent policy exception, use a narrow
[`[[overrides]]` entry](/sprawl-guard/configure-checks/) with a meaningful reason. Use [`tighten`](/sprawl-guard/clean-up-violations/) to record improvements; `update`
never lowers or removes ceilings.

Run the full repository check after an approval and commit the source and ratchet changes together.
Unchanged entries are omitted from the human summary, but remain in the ratchet and in
`--format toml` output.
