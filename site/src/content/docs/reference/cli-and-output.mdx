## Commands

### `init`

Creates `sprawl-guard.toml`, or the path selected by `--config`.

<CliCommandReference path="sprawl-guard init" />

`init` enables every supported language through the built-in defaults and refuses to overwrite an
existing configuration when writing.

### `languages`

Lists every supported language, or only the languages detected under the root. The report includes
configuration keys, bundled extensions and exact filenames, literate-language status, automatic
language groups, and automatic included line types. `--format` defaults to `human`.

<CliCommandReference path="sprawl-guard languages" />

### `check [PATHS]...`

Checks the whole repository when no paths are given, or only the supplied scopes.

<CliCommandReference path="sprawl-guard check" />

The two ratchet-current options conflict. A `warn` traversal policy can produce a successful but
partial report; explicit scope failures and failures reading measured source files remain errors.

### `update [PATHS]...`

Records newly discovered violations as ratchet ceilings. By default, output lists only added or
raised ceilings with their before-and-after values; `--write` applies the same changes. Existing
ceilings remain unchanged unless you pass `--allow-increases`. Use `--format toml` to print the
complete resulting ratchet, including unchanged entries.

<CliCommandReference path="sprawl-guard update" />

With no paths, it discovers violations across the repository. Path arguments limit discovery to the
selected scopes.

### `tighten [PATHS]...`

Lowers existing ratchet ceilings after violations improve. It never creates or raises ceilings.

<CliCommandReference path="sprawl-guard tighten" />

With no paths it evaluates the complete ratchet; path arguments restrict the update. Output lists
lowered or removed ceilings; `--format toml` prints the complete resulting ratchet. A write with no
ceiling changes preserves the existing file.

### Config inspection and upgrades

`resolved` prints the built-in defaults merged with the selected root configuration. It makes
inherited per-language limits on logical lines of code (LOC) and automatic literate-language line
types explicit. To list only the languages found under the root, use `languages --detected`.
`export` prints the complete policy suitable for committing. `upgrade` updates the authored root
config to the current schema; `--check` reports whether an update is required without changing the
file.

```sh title="Check Configuration Freshness"
sprawl-guard config upgrade --check
```

```sh title="Inspect Configuration"
sprawl-guard config resolved
sprawl-guard languages --detected
```

<CliCommandReference path="sprawl-guard config resolved" />

<CliCommandReference path="sprawl-guard config export" />

<CliCommandReference path="sprawl-guard config upgrade" />

### `schema {config|ratchet}`

Prints the selected JSON Schema for local or offline editor integration.

<CliCommandReference path="sprawl-guard schema" />

### `explain PATH`

Explains ignore handling, language ownership, test classification, effective limits, matching
overrides, the current logical-line measurement, and Rust `cfg(test)` handling for one path.

<CliCommandReference path="sprawl-guard explain" />

## Output formats

- Human output groups failures by file size, test file size, production directory fan-out, test
  directory fan-out, and ratchet state.
- JSON emits a structured report with root, requested scope, configuration and counter provenance,
  coverage, warnings, and violations.
- SARIF emits SARIF 2.1.0 for check results.

Human check output always identifies the selected authored config or reports that only built-in
defaults were used, including with `--quiet` and when traversal fails.

The default comes from `[output].format`; `check --format` takes precedence. Other diagnostic
commands that expose `--format` support only `human` and `json`.

A JSON report with one file violation looks like:

```json
{
  "status": "failed",
  "root": "/repo",
  "scope": {
    "kind": "all"
  },
  "config_source": {
    "kind": "authored",
    "path": "/repo/sprawl-guard.toml"
  },
  "coverage": {
    "kind": "complete"
  },
  "summary": {
    "files_checked": 12,
    "directories_checked": 4,
    "languages_detected": 2
  },
  "counter": {
    "backend": "tokei",
    "version": "14.0.0"
  },
  "warnings": [],
  "violations": [
    {
      "kind": "file_loc",
      "path": "src/large.py",
      "language": "Python",
      "included_line_types": ["code"],
      "line_counts": {
        "code": 430,
        "comments": 18,
        "blank_lines": 62
      },
      "actual": 430,
      "limit": 400,
      "ratchet": null
    }
  ]
}
```

`status` is `passed` or `failed` for a completed policy check. `scope` is `all` for an unscoped
request or for a root-equivalent path such as `.`, and `paths` with normalized paths for a scoped
request. `config_source` identifies the authored config path or reports that only built-in policy
was used. `summary` reports the number of source files, distinct source directories, and languages
checked. `coverage` independently reports whether traversal completed within the requested scope,
`counter` identifies the configured-LOC counter, and `warnings` and `violations` contain structured
diagnostics. Successful human output includes the same summary and calls out scoped checks or
built-in-only policy.

Collected traversal failures produce JSON with `status: "error"` when JSON is requested.
SARIF traversal failures produce human-readable stderr, not a SARIF report. Other operational
failures can also write only stderr. Check the exit code before parsing stdout.

```sh title="Check as SARIF"
sprawl-guard check --format sarif
```

### SARIF rule IDs

| Rule ID                              | Finding                                                |
| ------------------------------------ | ------------------------------------------------------ |
| `sprawl-guard/file-loc`              | Production file configured LOC exceeds the limit.      |
| `sprawl-guard/test-file-loc`         | Test file configured LOC exceeds the limit.            |
| `sprawl-guard/directory-fanout`      | Production leaf-file fan-out exceeds the limit.        |
| `sprawl-guard/test-directory-fanout` | Test leaf-file fan-out exceeds the limit.              |
| `sprawl-guard/ratchet-increase`      | A ratcheted measurement increased.                     |
| `sprawl-guard/ratchet-stale`         | A ratchet entry no longer matches a current violation. |

Configuration, path, I/O, parsing, and unrecoverable traversal diagnostics are operational errors,
not policy findings.

## Exit codes

Check the exit code before parsing the output of a command such as:

```sh title="Check as JSON"
sprawl-guard check --format json
```

| Code | Meaning                                                                                                            |
| ---- | ------------------------------------------------------------------------------------------------------------------ |
| `0`  | Command completed successfully; a check found no policy failures.                                                  |
| `1`  | A check found limit or ratchet violations, or `config upgrade --check` found an upgrade is required.               |
| `2`  | An operational error occurred in configuration, arguments, paths, I/O, parsing, traversal, or internal processing. |

The npm wrapper forwards these exit codes after launching the native CLI or WASI fallback. Wrapper
startup failures, such as an invalid fallback invocation, exit `1` with a diagnostic on stderr; that
code alone does not establish a policy violation.
