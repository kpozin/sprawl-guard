## Command line

Write each option after the command it belongs to, as in `sprawl-guard check --format json`. Run
commands from the repository root, or pass its path with `--root`.

<CliCommandReference path="sprawl-guard" />

The npm package includes native builds for macOS (x64 and Arm), Linux (x64 and Arm with glibc, x64
with musl), and Windows (x64). On other platforms it runs a slower WebAssembly build, which accepts
an absolute path only for `--root`. Write other paths relative to the repository root:

```sh
sprawl-guard check --root /repo src/file.rs
```

## Commands

### `init`

Previews `sprawl-guard.toml`, or the file that `--config` names. `--write` creates it.

<CliCommandReference path="sprawl-guard init" />

`init` enables every supported language through the built-in defaults and refuses to overwrite an
existing configuration when writing.

### `languages`

Lists every supported language, or only the languages detected under the root. Human output is a
table of language, key, and extensions. JSON adds bundled filenames, automatic language groups,
and automatic `count_lines`. `--format` defaults to `human`.

<CliCommandReference path="sprawl-guard languages" />

### `check [PATHS]...`

Checks the whole repository when no paths are given, or only the selected paths.

<CliCommandReference path="sprawl-guard check" />

`--require-ratchet-current` and `--no-require-ratchet-current` cannot be combined. With
`--unreadable-paths warn`, a check can pass with a partial report. An unreadable selected path or
source file is still an error.

### `update [PATHS]...`

Adds ratchet entries for new violations. By default it previews the added or raised ceilings with
their before-and-after values, and `--write` saves them. Existing ceilings stay unchanged unless you
pass `--allow-increases`. To print the complete resulting ratchet file, including unchanged
entries, use `--format toml`.

<CliCommandReference path="sprawl-guard update" />

With no paths, `update` covers the whole repository. With paths, it covers only those paths.

### `tighten [PATHS]...`

Lowers existing ratchet ceilings after violations improve. It never creates or raises ceilings.

<CliCommandReference path="sprawl-guard tighten" />

With no paths, `tighten` covers every ratchet entry. With paths, it covers only the entries under
them. The output lists lowered or removed ceilings, and `--format toml` prints the complete
resulting ratchet file. When no ceiling changes, `--write` leaves the file untouched.

### Inspect and upgrade the configuration

The `config` command has three subcommands:

- `config resolved` prints the built-in defaults merged with your configuration, including each
  language's inherited line limits and automatic `count_lines`.
- `config export` prints the complete configuration, ready to commit.
- `config upgrade` previews the configuration upgraded to the current schema. `--write` saves it,
  and `--check` saves nothing and exits `1` when an upgrade is pending.

To list only the languages found in the repository, use `languages --detected`.

```sh title="Check that the configuration is current"
sprawl-guard config upgrade --check
```

```sh title="Inspect the configuration"
sprawl-guard config resolved
sprawl-guard languages --detected
```

<CliCommandReference path="sprawl-guard config resolved" />

<CliCommandReference path="sprawl-guard config export" />

<CliCommandReference path="sprawl-guard config upgrade" />

### `schema {config|ratchet}`

Prints the selected JSON Schema for local or offline editor integration.

<CliCommandReference path="sprawl-guard schema" />

### `explain PATH`

Shows, for one path, whether it is ignored or excluded, which language claims it, whether it is a
test file, its limits, matching overrides, its current lines, and Rust `cfg(test)` handling.

A path that does not exist is still classified by its name, so you can see how Sprawl Guard would
classify a planned file. Human output says the path was not found, and JSON reports
`state: "not_found"` instead of `state: "measured"`.

The active config file and the ratchet file are never checked as source files. `explain` reports
them as `config_excluded` and `ratchet_excluded`.

<CliCommandReference path="sprawl-guard explain" />

## Output formats

- Human output groups failures under "Files over the line limit", "Test files over the line limit",
  "Directories with too many direct files", "Test directories with too many direct files", and
  "Ratchet failures". Each failure reads like
  `src/big.rs: 700 lines (limit 400)`. Paths are relative to the root and never quoted; control
  characters in them are escaped.
- JSON output is a structured report with the root, selected paths, where the configuration came
  from, the line counter, coverage, warnings, and violations.
- SARIF output follows SARIF 2.1.0 and covers check results.

Human check output starts with `Configuration: PATH`, or with
`Configuration: built-in defaults (no sprawl-guard.toml in ROOT)` when there is no config file. That
line appears even when the check stops on an unreadable path. With `--quiet`, a passing check prints
nothing, and a failing check prints only the configuration line and its failures.

`check` takes its default format from `[output].format`, and `check --format` overrides it. Other
commands ignore `[output].format` and default to `human`. `update` and `tighten` also support
`toml`, and `languages` and `explain` also support `json`.

A JSON report with one file violation looks like:

```json
{
  "status": "failed",
  "root": "/repo",
  "paths": "all",
  "config_source": {
    "kind": "authored",
    "path": "/repo/sprawl-guard.toml"
  },
  "counter": {
    "backend": "tokei",
    "version": "15.0.0"
  },
  "coverage": {
    "kind": "complete"
  },
  "summary": {
    "files_checked": 12,
    "directories_checked": 4,
    "languages_detected": 2,
    "ratchet_entries": 0
  },
  "warnings": [],
  "violations": [
    {
      "kind": "file_lines",
      "path": "src/large.py",
      "language": "Python",
      "count_lines": [],
      "line_counts": {
        "code": 430,
        "comments": 18,
        "blank_lines": 62
      },
      "actual": 430,
      "limit": 400,
      "ratchet": null
    }
  ]
}
```

The report fields are:

- `status`: `passed` or `failed` for a completed check.
- `paths`: `"all"` for the whole repository, including a root path such as `.`; otherwise a list of
  normalized selected paths.
- `config_source`: the config file used, or that only built-in defaults were used.
- `counter`: the line counter.
- `coverage`: whether every selected path could be read.
- `summary`: the number of source files, distinct source directories, and languages checked, plus
  the number of remaining ratchet entries. Passing human output shows the same summary.
- `warnings` and `violations`: structured diagnostics.

When a path cannot be read, `check --format json` still prints a JSON report with `status: "error"`,
and `check --format sarif` prints only a message on stderr. Other errors may also print only to
stderr, so check the exit code before parsing stdout.

```sh title="Check as SARIF"
sprawl-guard check --format sarif
```

### SARIF rule IDs

| Rule ID                                    | Finding                                                         |
| ------------------------------------------ | --------------------------------------------------------------- |
| `sprawl-guard/file-lines`                  | A source file has more lines than its limit.                    |
| `sprawl-guard/test-file-lines`             | A test file has more lines than its limit.                      |
| `sprawl-guard/directory-direct-files`      | A directory directly contains more source files than its limit. |
| `sprawl-guard/test-directory-direct-files` | A directory directly contains more test files than its limit.   |
| `sprawl-guard/ratchet-increase`            | A measurement rose above its ratchet ceiling.                   |
| `sprawl-guard/ratchet-stale`               | A ratchet entry's violation shrank or disappeared.              |

Configuration, path, I/O, parsing, and unreadable-path problems are errors, not violations.

## Exit codes

Check the exit code before you parse JSON or SARIF output:

```sh title="Check as JSON"
sprawl-guard check --format json
```

| Code | Meaning                                                                                              |
| ---- | ---------------------------------------------------------------------------------------------------- |
| `0`  | The command succeeded. For a check, it found no violations.                                          |
| `1`  | A check found violations, or `config upgrade --check` found a pending upgrade.                       |
| `2`  | An error in configuration, arguments, paths, I/O, parsing, unreadable paths, or internal processing. |

The npm package uses the same exit codes. If it can't start Sprawl Guard, it exits `2` with a
message on stderr.
